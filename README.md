# Обзор датасетов для Robotics

# Типы задач в Robotics
[Можно выделить две основные](https://arxiv.org/abs/2408.03539)  группы задач:
![Типы задач в robotics](Pasted%20image%2020261026011620.png)
## 1. Single-Robot Competencies
### 1.1. Mobility (передвижение)
- **Locomotion** — управление движением робота: ходьба, бег, прыжки, поддержание равновесия, управление квадрокоптером. Основной акцент — на динамике движения и низкоуровневом управлении.
- **Navigation** — перемещение к заданной цели с учётом препятствий и структуры окружающего пространства. Основной акцент — на выборе маршрута и достижении цели.
### 1.2. Manipulation — взаимодействие с объектами
- **Stationary Manipulation** — манипуляции объектами с помощью робота с неподвижным основанием. Включает grasping, pick-and-place, assembly, in-hand manipulation.
- **Mobile Manipulation** — сочетание передвижения и манипуляции. Например, робот должен подъехать к объекту, захватить его и переместить в другое место.
## 2. Multi-Agent Competencies (нам не так интересно)
Задачи, предполагающие взаимодействие робота с другими агентами.
- **Human-Robot Interaction (HRI)** — взаимодействие и совместная работа человека и робота, включая shared autonomy и физическое сотрудничество.
- **Multi-Robot Interaction** — координация нескольких роботов, совместное выполнение задач, избегание столкновений и коллективное принятие решений.
## Связь с Offline RL и датасетами

Каждая из этих задач потенциально может быть сформулирована как задача Reinforcement Learning, где робот взаимодействует со средой и выбирает действия для максимизации суммарной награды.

В Offline RL обучение происходит на заранее собранном фиксированном наборе траекторий: $\mathcal{D}=\{\tau_1,\ldots,\tau_N\}$,  где каждая траектория состоит из последовательности состояний, действий и наград. 

- В основном задачи Robotics решаются с помощью RL и imitation learning (обучение следовать заранее заданным траекториям). 
- **Online RL (датасет формируется во время обучения, с помощью взаимодействия со средой) подходит для нашего исследования меньше, так как в такой постановке нельзя будет сравнивать разные архитектуры на идентичных наборах данных. Также добавляется слой работы с симулятором, которого можно избежать в offline RL**  
## Sate-based датасеты 
В робототехнике датасеты можно разделить по типу наблюдений, которые получает модель.

|                        | State-based datasets                     | Vision-based datasets                         |
| ---------------------- | ---------------------------------------- | --------------------------------------------- |
| Наблюдение             | Вектор числовых признаков                | Изображение или видео                         |
| Пример                 | Положения суставов, скорости, координаты | Изображения с камер робота                    |
| Размерность наблюдения | Обычно десятки или сотни чисел           | Тысячи или миллионы значений                  |
| Обработка входа        | Обычно линейная проекция                 | CNN, ViT или другой visual encoder            |
| Основная сложность     | Динамика системы и временные зависимости | Визуальное восприятие + временные зависимости |
| Примеры                | D4RL: Hopper, AntMaze                    | RoboNet, визуальные задачи BridgeData         |

Для исследования последовательностных архитектур (SSM, Transformers, RNN) особый интерес представляют датасеты с низкоразмерными состояниями, позволяющие изучать временные зависимости без необходимости обрабатывать изображения.

# Детальнее про датасеты

Ниже описаны среды, в каждой из которых есть несколько датасетов. Датасеты внутри одной среды могут различаться условиями сбора данных, качеством траекторий и вариантами задач.
## 1. D4RL

[D4RL: Datasets for Deep Data-Driven Reinforcement Learning](https://arxiv.org/abs/2004.07219) — benchmark, состоящий из нескольких датастов для offline RL. 
Раньше у датасета был свой репозиторий, сейчас с ним можно работать через [Minari](https://github.com/Farama-Foundation/Minari) 
### 1.1. MuJoCo locomotion: HalfCheetah, Hopper, Walker2d

**Задача.** Робот должен двигаться вперёд по ровной поверхности, управляя суставами. Движение моделируется в физическом симуляторе MuJoCo. Рассматриваются три конструкции: HalfCheetah — бегущая модель с двумя конечностями, Hopper — одноногий прыгающий робот, Walker2d — двуногий шагающий робот.

На шаге $t$ робот получает наблюдение $o_t$, выбирает действие $a_t$, после чего симулятор вычисляет новое состояние и награду $r_t$. Цель управления — максимизировать суммарную награду за эпизод:
$$
G=\sum_{t=0}^{T-1}r_t.
$$
Награда поощряет скорость движения вперёд и штрафует большие управляющие воздействия. В Hopper и Walker2d также предусмотрен бонус за сохранение допустимой позы; падение завершает эпизод. [Реализации сред: HalfCheetah](https://github.com/openai/gym/blob/0.23.1/gym/envs/mujoco/half_cheetah.py), [Hopper](https://github.com/openai/gym/blob/0.23.1/gym/envs/mujoco/hopper.py), [Walker2d](https://github.com/openai/gym/blob/0.23.1/gym/envs/mujoco/walker2d.py).

**Наблюдения и действия.** Состояние механической системы описывают координаты $q_t$ и скорости $\dot q_t$. Модель получает числовое наблюдение:
$$
o_t=(z_t,\theta_t,\boldsymbol{\alpha}_t,\dot x_t,\dot z_t,\dot\theta_t,\dot{\boldsymbol{\alpha}}_t),
$$
где $z_t$ — высота корпуса, $\theta_t$ — его наклон, $\boldsymbol{\alpha}_t$ — углы суставов, остальные компоненты — соответствующие скорости. Абсолютная горизонтальная координата $x_t$ исключена: для движения по однородной поверхности важно, как робот движется, а не где он находится.

**Датасеты.** D4RL предоставляет заранее записанные последовательности наблюдений, действий и наград, а также признаки завершения эпизодов. Это данные поведения других алгоритмов: при offline-обучении модель использует фиксированный набор, не собирая новые взаимодействия. [Формат D4RL](https://github.com/Farama-Foundation/D4RL).

Для каждой среды есть варианты данных:

| Вариант         | Источник                                                                          |
| --------------- | --------------------------------------------------------------------------------- |
| `random`        | Политика — алгоритм выбора действий — со случайно инициализированными параметрами |
| `medium`        | Частично обученная политика                                                       |
| `expert`        | Полностью обученная политика с высоким результатом                                |
| `medium-replay` | Данные, накопленные в процессе обучения до уровня `medium`                        |
| `medium-expert` | Смесь данных `medium` и `expert` примерно поровну                                 |

Например, `hopper-medium-v2` обозначает среду Hopper, способ сбора данных `medium` и версию набора `v2`. [Описание вариантов](https://github.com/Farama-Foundation/d4rl/wiki/Tasks).

**Для нашего исследования.** Можно сравнить предсказание действий по текущему наблюдению и по истории разной длины. Качество управления оценивается суммарной наградой в симуляторе. Польза длинной истории здесь — проверяемая гипотеза.
### 1.2. Maze2D и AntMaze

**Задача.** Агент должен добраться из начальной позиции в заданную точку лабиринта, обходя стены. В Maze2D агент — шарик, движущийся по плоскости; в AntMaze — четырёхногий робот Ant. Поэтому Maze2D проверяет преимущественно навигацию, а AntMaze дополнительно требует координации суставов для передвижения. [Описание сред D4RL](https://github.com/Farama-Foundation/d4rl/wiki/Tasks).
Цель задаётся координатами $g=(x_g,y_g)$. Она считается достигнутой, если агент оказался достаточно близко:
$$
\|p_t-g\|_2\leq\varepsilon,
\qquad p_t=(x_t,y_t),
$$
где $p_t$ — текущая позиция, а $\varepsilon=0.5$ — порог расстояния в единицах симулятора. При разреженной награде:
$$
r_t=\mathbf{1}\{\|p_t-g\|_2\leq\varepsilon\}.
$$
То есть награда равна 1 около цели и 0 в остальных точках. Такое правило используется в [Maze2D](https://github.com/Farama-Foundation/D4RL/blob/master/d4rl/pointmaze/maze_model.py) и [AntMaze](https://github.com/Farama-Foundation/D4RL/blob/master/d4rl/locomotion/goal_reaching_env.py).
**Наблюдения и действия.**

| | Maze2D | AntMaze |
|---|---|---|
| Наблюдение $o_t$ | $x,y$ и скорости $\dot x,\dot y$ — **4 числа** | Положение корпуса $x,y,z$, ориентация корпуса — 4 числа, 8 углов суставов, 14 линейных и угловых скоростей — **29 чисел** |
| Действие $a_t$ | **2 сигнала**: силы вдоль осей $x,y$ | **8 сигналов**: управление приводами суставов |
| Диапазон действий | $[-1,1]^2$ | $[-1,1]^8$ |

В AntMaze ориентация представлена четыремя числами, кодирующими поворот тела в трёхмерном пространстве. Здесь указан стандартный состав наблюдения D4RL AntMaze при оценке: он включает абсолютные координаты $x,y$, необходимые для навигации. [Реализация AntMaze](https://github.com/Farama-Foundation/D4RL/blob/master/d4rl/locomotion/ant.py).

Карта лабиринта и координаты цели **не входят в эти векторы наблюдений**. Геометрия лабиринта фиксирована для выбранной среды. Если обучать модель достигать разных целей, $g$ нужно подавать отдельно:
$$
a_t=\pi_\theta(o_{\leq t},a_{<t},g),
$$
где $\pi_\theta$ — обучаемая модель выбора действий. [Maze2D](https://github.com/Farama-Foundation/D4RL/blob/master/d4rl/pointmaze/maze_model.py), [наблюдение AntMaze](https://github.com/Farama-Foundation/D4RL/blob/master/d4rl/locomotion/goal_reaching_env.py).

**Датасеты.** Данные содержат записанные перемещения между целями. Цели при сборе могут отличаться от цели, которую потребуется достичь при проверке.

| Семейство | Варианты |
|---|---|
| Maze2D | `open` — открытая площадка; `umaze` — U-образный лабиринт; `medium`, `large` — более сложные лабиринты. Есть варианты с разреженной и плотной наградой |
| AntMaze | `umaze`, `medium`, `large`; `diverse` — перемещения к случайным целям; `play` — перемещения между выбранными авторами начальными и целевыми позициями |

У Maze2D данные образуют непрерывную траекторию со сменой целей. Поле `timeouts` отмечает достижение очередной цели при сборе и позволяет разделить запись на фрагменты. [Описание данных и вариантов](https://github.com/Farama-Foundation/d4rl/wiki/Tasks).

**Для нашего исследования.** Можно обучать предсказанию действий с условием на цель, выбирая обучающую цель из будущих позиций той же траектории. Основная метрика — доля успешных достижений цели в симуляторе.
### 1.3. FrankaKitchen

**Суть задачи.** Рука Franka взаимодействует с микроволновкой, чайником, переключателем света, шкафчиками и ручками плиты. Цель — выполнить заданную комбинацию подзадач, например открыть микроволновку и шкафчик, переместить чайник и включить свет. Используем числовые состояния без изображений: `observation` содержит 59 признаков (положения и скорости робота и объектов), `achieved_goal` — текущие конфигурации целевых объектов, `desired_goal` — желаемые. Действие — вектор из 9 компонент, управляющих скоростями суставов руки и пальцев захвата. [Документация среды](https://robotics.farama.org/envs/franka_kitchen/franka_kitchen/).

**Наш эксперимент: предсказание действий с условием на цель (goal-conditioned behavioral cloning).** Обучаем модель подражать действиям демонстратора:

$$
\hat a_t = \pi_\theta(o_{t-L+1:t},\; a_{t-L+1:t-1},\; g),
\qquad
\mathcal L = \mathbb E_{\mathcal D}\left[\|\hat a_t-a_t\|_2^2\right],
$$

где $o_t$ — наблюдение, $a_t$ — действие, $g$ — цель, $L$ — длина истории. Начальный вариант использует среднюю квадратичную ошибку действий. Цель задаём как конфигурации объектов и маску требуемых подзадач, чтобы различать «этот объект не входит в цель» и «ему задано конкретное положение». Поля `info`, сообщающие о выполнении подзадач, используем для оценки, а не как вход модели.

**Интуиция и предполагаемые операции.** Модель должна выбирать следующий навык с учётом цели и прогресса, а затем управлять рукой. Это кандидат для проверки композиции навыков и отслеживания состояния, но необходимость истории заранее не гарантирована: открытая дверца или положение чайника уже могут показывать выполненные этапы. Базовое сравнение — модель по текущему наблюдению и цели $\pi(o_t,g)$ против моделей с историей при сопоставимом числе параметров и одинаковом обучении. Изменяя $L$, проверяем, даёт ли история дополнительную информацию.

**Метрики.** Основная оценка — самостоятельные запуски обученной модели в симуляторе:

- среднее число различных целевых подзадач, выполненных хотя бы раз за эпизод;
- доля эпизодов, в которых выполнены все требуемые подзадачи;
- отдельно, при необходимости, доля эпизодов, где все целевые объекты одновременно находятся в нужных конфигурациях в конце.

**Почему полезно:** задача проверяет преимущества последовательностных архитектур в длительном управлении и сочетании навыков, однако для устойчивого сравнения требуется больше данных, чем 19 эпизодов `complete-v2`.
## 2. robomimic low-dim

**Формально.** Для выбранной задачи дан фиксированный набор демонстраций $\mathcal D=\{\tau_i\}_{i=1}^{N}$, где $\tau_i=(o_0,a_0,\ldots,o_{T_i-1},a_{T_i-1},o_{T_i})$, $o_t\in\mathbb R^{d_o}$ — числовые признаки робота и объектов, а $a_t\in\mathbb R^{d_a}$ — управляющее действие; обучаем модель $\hat a_t=\pi_\theta(o_{t-L+1:t},a_{t-L+1:t-1})$ воспроизводить действия демонстратора и оцениваем долю самостоятельных выполнений задачи в симуляторе.

**Задача.** robomimic — набор данных и инструментов для обучения манипуляции по демонстрациям, включающий несколько задач в симуляторе robosuite:

| Среда     | Что должен сделать робот                                                                           |
| --------- | -------------------------------------------------------------------------------------------------- |
| Lift      | Захватить и поднять кубик                                                                          |
| Can       | Перенести банку в заданный отсек                                                                   |
| Square    | Надеть квадратную гайку на соответствующий штырь                                                   |
| Transport | Двумя руками перенести предмет из одного контейнера в другой, предварительно убрав крышку и помеху |
| Tool Hang | Установить рамку в основание и повесить на неё инструмент                                          |

![Изображение датасета](Pasted%20image%2020261026184615.png)
- Lift и Can проверяют более простые манипуляции, а Square, 
- Transport и Tool Hang требуют точного совмещения объектов или нескольких согласованных этапов; в отличие от Franka Kitchen, здесь каждая среда задаёт конкретную задачу, а не произвольную комбинацию кухонных подзадач.
- [Описание задач и исследования](https://robomimic.github.io/study/).

**Наблюдения и действия.** В варианте `low_dim` модель получает числовые признаки без изображений: положение и ориентацию захвата, положения его пальцев и признаки объектов, причём для Transport включаются обе руки, а размерность объектных признаков зависит от задачи. [Конфигурации наблюдений авторов](https://github.com/ARISE-Initiative/robomimic/blob/master/robomimic/scripts/generate_paper_configs.py).

При стандартном управлении позой захвата действие для одной руки состоит из 7 чисел — трёх компонент смещения, трёх компонент поворота и команды захвату, а для двух рук Transport — из 14; конкретный способ управления фиксируется метаданными выбранного датасета. [Контроллеры robosuite](https://robosuite.ai/docs/modules/controllers.html).
**Датасеты.** Используем готовые HDF5-файлы `low_dim` с наблюдениями, действиями и наградами, где каждая демонстрация хранится отдельно, а метаданные позволяют восстановить соответствующую среду. [Структура данных](https://robomimic.github.io/docs/datasets/overview.html).

| Вариант | Источник демонстраций | Доступные задачи в наборе CoRL 2021 |
| --- | --- | --- |
| PH — Proficient Human | 200 успешных демонстраций опытного оператора; в Transport — двух операторов, работающих вместе | Lift, Can, Square, Transport, Tool Hang |
| MH — Multi-Human | 300 демонстраций операторов разного уровня; в Transport — пар операторов | Lift, Can, Square, Transport |
| MG — Machine-Generated | Траектории алгоритма на разных стадиях обучения | Lift, Can |
PH позволяет исследовать обучение на качественных демонстрациях, а MH — влияние различий в стиле и уровне управления; версии robomimic, robosuite и файлов данных нужно фиксировать, поскольку обновлённые наборы могут давать результаты, отличающиеся от CoRL 2021. [Источники демонстраций](https://robomimic.github.io/study/), [каталог и версии](https://robomimic.github.io/docs/datasets/robomimic_v0.1.html).
**Наш эксперимент.** Обучаем отдельную модель для каждой задачи воспроизводить действия демонстратора по истории наблюдений и предыдущих действий:

$$
\hat a_t = \pi_\theta(o_{t-L+1:t}, a_{t-L+1:t-1}),
\qquad
\mathcal L = \mathbb E_{\mathcal D}\left[\|\hat a_t-a_t\|_2^2\right],
$$

где $L$ — длина истории, а отдельную цель $g$ в начальном эксперименте не подаём, поскольку задача фиксирована выбранной средой.

# Как сравнивать архитектуры

## Постановка обучения

Ниже — предложенный план сравнения на основе существующих подходов, а не готовый протокол одной статьи: для каждой постановки указаны литературный ориентир и границы заимствования.

Обозначения: $o_t$ — наблюдение робота и объектов, $a_t$ — действие, $r_t$ — награда, $g$ — желаемая конфигурация или координаты цели, $L$ — длина истории, $T$ — длительность эпизода, а знак $\hat{\phantom{a}}$ обозначает предсказание модели.

Кратко обозначим доступную историю как $h_t=(o_{t-L+1:t},a_{t-L+1:t-1})$: модель видит текущее наблюдение и прошлые действия, но не действие, которое должна предсказать; $R_t=\sum_{k=t}^{T-1}r_k$ — return-to-go, то есть сумма наград от текущего шага до конца эпизода.

| Постановка                                                 | Вход → предсказываемая величина                                                          | Где используем                                                        | Что оцениваем                                                                 | Источник подхода                                                                                                                                                                  |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Behavior Cloning (BC) — подражание демонстрациям           | $h_t\rightarrow\hat a_t$: история → действие                                             | robomimic; базовый вариант для MuJoCo locomotion                      | Ошибку действий и успешность управления                                       | [Mandlekar et al., What Matters…, CoRL 2021](https://arxiv.org/abs/2108.03298): BC и BC-RNN на человеческих демонстрациях                                                         |
| Goal-conditioned BC (GCBC) — подражание с условием на цель | $(h_t,g)\rightarrow\hat a_t$: история и цель → действие                                  | Maze2D / AntMaze; FrankaKitchen при наличии подходящих целей в данных | Долю достижений заданной цели; для Kitchen — также число выполненных подзадач | [Ghosh et al., Learning to Reach Goals via Iterated Supervised Learning, ICLR 2020](https://arxiv.org/abs/1912.06088): обучение на траекториях с условием на достигнутую цель     |
| Предсказание действий с условием на return-to-go           | $(h_t,R_{t-L+1:t})\rightarrow\hat a_t$: история и значения оставшейся награды → действие | Дополнительный эксперимент на MuJoCo locomotion                       | Суммарную награду в симуляторе при заданном желаемом return-to-go             | [Chen et al., Decision Transformer, NeurIPS 2021](https://arxiv.org/abs/2106.01345): метод Decision Transformer                                                                   |
| Dynamics prediction — прогноз динамики                     | $(h_t,a_t)\rightarrow\hat o_{t+1}$: история и выбранное действие → следующее наблюдение  | Дополнительная проверка на любом выбранном наборе                     | Ошибку прогноза наблюдений; при последовательном прогнозе — накопление ошибки | [Janner et al., Trajectory Transformer, NeurIPS 2021](https://arxiv.org/abs/2106.02039): ориентир по моделированию траекторий, а не источник именно нашего одношагового протокола |

**О названиях.** Decision Transformer — оригинальное название метода Chen et al., а добавление `-style` обозначает нашу постановку с таким же условием на return-to-go при сравнении разных архитектур; dynamics prediction — общепринятое название задачи прогноза динамики, тогда как метод Janner et al. называется Trajectory Transformer и моделирует траектории целиком.

**BC и robomimic.** Наиболее прямой ориентир — работа Mandlekar et al.: из неё берём задачи манипуляции, варианты демонстраций PH/MH, сравнение обучения с историей и без неё и оценку успешности в симуляторе; сами BC и рекуррентные политики появились раньше этой работы, а наша замена последовательностной архитектуры требует отдельного согласования входов, функции потерь и бюджета обучения.

**GCBC и навигация.** Идея выбирать цель из будущего той же траектории соответствует подходу Ghosh et al.: записанное действие рассматривается как пример движения к действительно достигнутому состоянию; однако их алгоритм GCSL итеративно собирает новые данные, а мы предлагаем только offline-адаптацию на фиксированных траекториях Maze2D / AntMaze, без воспроизведения всей процедуры статьи.

**GCBC и Kitchen.** Источник самой среды и многоэтапных задач — [Gupta et al., Relay Policy Learning, CoRL 2019](https://arxiv.org/abs/1910.11956), где используются иерархические политики с условием на цель и последующее дообучение через взаимодействие со средой; предложенная здесь единая модель GCBC, маска требуемых подзадач и тест на исключённых комбинациях — наша адаптация для сравнения архитектур, которую нельзя приписывать этой статье как готовый протокол.

**Return-to-go и MuJoCo.** Здесь постановка непосредственно следует Decision Transformer: на обучении подаём сумму будущих наград $R_t=\sum_{k=t}^{T-1}r_k$, на оценке задаём желаемое значение и уменьшаем его на получаемые награды; это позволяет обусловить поведение желаемым результатом на данных разного качества, тогда как обычный BC воспроизводит записанное поведение без такого условия.

**Прогноз динамики.** Trajectory Transformer моделирует распределение последовательностей состояний, действий и наград и использует поиск для планирования, поэтому предложенный здесь отдельный прогноз $\hat o_{t+1}=f_\theta(o_{\leq t},a_{\leq t})$ — упрощённая диагностическая задача, а не воспроизведение его метода или полноценная политика управления.

**Почему постановки различаются.** В robomimic задача фиксирована выбранной средой, в навигации и Kitchen нужно сообщить модели желаемую цель, а return-to-go задаёт желаемое качество поведения, причём одинаковая суммарная награда не определяет, какие именно подзадачи Kitchen должны быть выполнены.

**Что сравниваем.** Основной этап — BC на robomimic и GCBC на выбранных задачах достижения цели; return-conditioned обучение и прогноз динамики остаются дополнительными экспериментами, а архитектуры сравниваем внутри одной постановки на одинаковых данных, поскольку изменение алгоритма вместе с архитектурой не позволяет отделить их вклад.
